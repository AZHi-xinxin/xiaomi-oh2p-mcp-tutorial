# 故障排查与验收

| 现象 | 怎么判断 |
| --- | --- |
| USB identify 一直失败 | 型号、数据线、原电源、启动窗口、驱动/USB 权限；先不执行写入 |
| 工具 success 却没内容 | 看实际输出长度；bulkcmd printenv 可能不返回正文 |
| 写一半断开 | 不算成功；保留原槽位和日志，不自动切启动槽或循环重刷 |
| 刷完 SSH 不通 | boot_part 是否与写入槽匹配、Wi-Fi 地址、是否持有对应私钥、Dropbear 是否实际启用 |
| 公钥正确但无人值守失败 | BatchMode 是否能登录，agent 是否可用于服务；查专用 Host 算法兼容 |
| Host key changed | 停止，核对是否自己重新生成的固件/换设备；不直接关验证 |
| 发声命令成功却听不到 | PCM 格式和 Playback 设备、原生音乐互斥、实际音量；回执不代替真人听感 |
| 麦克风几乎静音 | 检查 S32_LE 和通道布局，不能随意按 S16 或下混参考通道 |
| 唱歌时必须贴近唤醒 | 检查削顶及参考通道；先 AEC 再增益，不能只继续调灵敏度 |
| 歌词自己触发唤醒 | 调整 KWS 阈值并实测，暂停后丢弃旧帧，无真实新话不投递 |
| 点歌只有约一分钟 | 原厂曲库可能给试听，不是本工具能解锁会员 |
| 音乐状态超时 | 操作可能已执行，先查询状态，不重复发送相同动作 |
| MCP 重启后旧聊天工具失败 | 重新初始化/刷新连接；避免重放“结果未知”的旧调用 |
| 手机无回应但快捷灯正常 | 两条路线分开；查 Orbis 绑定与网络，不重刷音箱 |
| 自定义唤醒突然没回应，原厂语音仍正常 | 在常开主机查监听器的 ActiveState/SubState、最新状态时间与 journal；出现 Start request repeated too quickly 时，按第四篇恢复并配置 30 秒重试 |
| 监听器 active，但手机没有接到文字 | 检查手机 Web 服务绑定地址、事件来源、目标助手和原窗口；手机只绑定 127.0.0.1 时外部主机无法回传，离开家庭 Wi-Fi 后原 LAN 地址也不再可达 |
| 自定义音色能回应，语音能入窗，却不能控灯 | 先在同一窗口用键盘测试灯控；依下面的分层排查区分家电 MCP 与语音桥问题 |
| 找不到外部来源新增按钮或专用事件令牌 | 公开 v2.6.15 没有完整自助配置入口，见第四篇的版本说明；不是漏点了一个按钮 |
| 原生事件 401/400/409 | 分别核对专用凭证、允许的 source、有效绑定/目标；不要复用 Web 密码或换事件 ID 盲目重投 |
| 拔 USB 后不工作 | 确认日常用的是 Wi-Fi SSH、主机不睡眠，音箱仍有电源 |

## 第一次验收顺序

1. 未改原厂槽位的备份可读，目标镜像读回哈希匹配，版本与根分区正确。
2. 拔掉 USB 仅留电源，Wi-Fi 无交互 SSH 正常。
3. MCP 无认证被拒、正确认证能列出两个工具。
4. 简短 `speaker_say` 真人听见；TTS 密钥未进入工具输出。
5. 原厂点歌、暂停、继续真人核对；权限/试听限制如实说明。
6. 搬到日常位置后断电重连仍可用。
7. 若另外实现监听器，再测唤醒和大音乐、歧义/取消、原对话绑定及长期误唤醒。

当前实例前六项与语音关键场景已有现场验收；公开示例从零复装、其它机型、长期误唤醒和原厂回滚演练仍未覆盖。教程整理本身没有重新刷机、录音或播放。

2026-10-31 启动次数限制故障恢复后，维护者再次确认自定义唤醒正常。此次没有人为制造长时间断网或反复断电；长期重连行为仍需后续观察。

## 能唤醒、能回话，但不能开关灯

自定义唤醒后能听到 ElevenLabs、MiniMax 等音色，说明至少唤醒提示和播放链路有响应。它不证明后续语音已完整识别、模型已经调用家电工具，或灯具真的改变状态。按下面顺序只测一个设备、一次动作，避免重复开关。

1. **先看同一窗口能否用键盘控灯。** 在接收语音的那个助手、那个窗口，输入一条明确指令。观察实际工具名、参数、执行结果，并人工确认灯的状态。只看到“已经开了”的文字不能算通过。
2. **键盘也不行，先查家电工具。** 确认家电 MCP 在线，能列出目标设备；工具已给这个助手启用，必要审批已完成，没有被暂停。音箱 MCP 的 `speaker_say`/`speaker_music` 不提供灯控，需要另接 HA/米家等设备工具。核验配置后再做一次有明确目标的实际操作。
3. **键盘可以、语音不行，再查语音桥。** 在本机核对 ASR 最终文字是否完整、有无被唤醒回应截断，投递的助手和会话 ID 是否相同，消息是否真的触发新回复。外部事件还要检查有效绑定和 `wake`；聊天桥则检查自己的发送流程。不要因为文字“出现在某个窗口”就假设已经调用模型。
4. **有工具调用仍未执行，查动作回执。** 看是否选错房间/实体，是否等待审批，HA/设备是否超时。超时是结果未知，应先查询实际状态；不能把请求已发送或缓存中的旧状态当成实体已成功，也不能自动再发一次。
5. **灯变了却说没成功，区分状态确认与动作。** 有些设备状态同步延后，有些集成会乐观更新。记录动作时间和后续实际状态，以便排查“操作成功但确认超时”；不要用加一段“务必说成功”的提示词掩盖问题。
6. **灯控制正常但没声音，最后查 TTS 出口。** 查看是否确有 `speaker_say`/播放调用、播放是否被占用、音量与输出设备是否正确。终端返回 0 或模型说“我说完了”，仍需人类听见才算播报通过。

如果想让短指令走本地快捷控制，必须另接第四篇所述的快捷路由。保留聊天控制也可以，不必为了修这次问题先迁移到原生事件或重做整套监听器。

### 反馈时提供这个小样本即可

- 音箱型号、固件、Orbis 版本；用普通聊天桥还是原生事件入口。
- 同一窗口键盘控灯是否成功；一次语音的识别文字（自行打码）。
- 实际调用的工具名、脱敏参数、HTTP/工具错误码；实体是否真的改变。
- 若经原生事件入口：`bound/valid` 与回执状态；目标是否与键盘测试相同。
- 若只是声音卡顿：单独说明“生成慢”“开始播放慢”“声音断裂”或“完全没声音”。这几种现象不能都归成模型慢或网络差。

不要上传完整聊天、录音、家庭位置、账号、凭证或已认证链接。缺少上述执行证据时，只能定位到可疑环节，不能断言已经修复。

## 可提交的问题信息

版本、型号、错误码、阶段、是否 USB/SSH/MCP 哪一层失败。不要上传厂商账号、API Key、私钥、已认证 URL、家庭录音或完整聊天。原始固件和设备备份留在自己受限目录，不放 Git。

## 停用与升级

先停止你自己的语音监听服务，再停 `oh2p-mcp`；只移除自己加的 Serve 端口，保留其它服务。停软件不等于恢复原厂固件。需要切槽/回滚时按第二篇核对，不能套用别人的槽位号。

升级先在独立目录验证依赖和协议。若改变音频上传去向或云服务商，先更新人类看到的说明和选择；不能把既有本地识别配置悄悄改成云端。
